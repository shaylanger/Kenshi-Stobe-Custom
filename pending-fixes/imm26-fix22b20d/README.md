# imm26 fix22b20d: server fixes for rows 22-b and 20-d (found by 4080-i3op25)

OFFLINE, NOT deployed anywhere. Base = imm26 compose + huntA + durableA (`/root/imm26/comp2627-server`, staged as `/root/imm26/fix22b20d-base`; the touched files `lib/imm26_plans.php` and `lib/travel_companionship.php` are byte-identical to the 5090 i5 lane site).

## Fixes
- **22-b** (`lib/imm26_plans.php`): `stobeImm26PlanReportQueuePending` no longer queues a `plan_report` directive for a COMPLETED trip whose arrival remark was already claimed (`situated_remark_claim` with `event_id` `trip:<agreement_id>:completed`); the trip is marked `execution.reported` instead. Root cause: the bored tick claimed the situated arrival event (first remark); the next bored tick found the COMPLETED trip still unreported, queued `plan_report`, and `Bored event taken by negotiation directive` spoke a second arrival remark. Control: a completed trip with no claim still queues its farewell report.
- **20-d** (`lib/imm26_plans.php`, `lib/travel_companionship.php`): real chain in the run: s3 parked `pending_change`; the insistence turn confirmed it (old trip ended, `pending_replacement` Stumble Inn written, never cleared, no age limit); save+load failed the old trip (FAILED); the bare "Yes." prompt carried "propose it again now" but the model PROPOSEd the old Squin (the recorded FAILED agreement) and capture accepted it. Now, when the old trip is not PROPOSED/ACCEPTED and a fresh (<= 6 game hours) `pending_replacement`, or a `pending_change` naming that dead old agreement, exists, a bare confirmation (no negation, no other place named, `stobeImm26LineNegates` / `stobeImm26LineNamesOtherPlace`) replaces the model's destination/kind/leader with the waiting change and turns ACCEPT into PROPOSE; the waiting record is cleared after the PROPOSE row is written; if the model named another place the reply text is replaced by "All right, <dest> it is. Shall we head there?". Prompt tail: dead old trip gets an explicit PROPOSE instruction; `pending_replacement` now expires like `pending_change`; the pending_change "trip stays in force" text only shows while the old trip is ACCEPTED.
- Design note: the PROPOSE is not an instant ACCEPT because `pending_replacement` stores no destination point (the next "Yes" accepts the fresh offer through the normal path, tested). The row check accepts PROPOSE/ACCEPT of the new destination.
