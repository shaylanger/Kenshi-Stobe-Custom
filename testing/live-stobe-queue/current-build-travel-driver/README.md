# Current-build P0 travel start and movement row

`driver.sh` / `driver.py` run a real two-turn lifecycle through existing `stobe-auto` handlers. Supported routes are isolated 4080 i3 (`KENSHI_DIR=/c/KenshiInst/3`, `KAH_DIR=C:\KenshiInst\3\mods\AutomationHarness`) and isolated 5090 i3 (`KENSHI_DIR=/mnt/d/KenshiInst/3`, `KAH_DIR=D:\KenshiInst\3\mods\AutomationHarness`). The driver rejects other paths, including either rig's i1/main route. Source the documented `tools/automation/rig-env.sh` for the selected route before invocation.

The row requires fresh `PREFLIGHT_RECEIPT` and `DESTINATION_RECEIPT` files from the owner. They must cover the copied save, exact current build, private backend/session, input isolation, inbox gate, supported destination and route feasibility. `OUT` must be a new path whose parent already exists; one atomic directory creation claims it, and an existing path fails before any KAH handler runs. Supply the exact current display name from `stobe_state` (including template suffixes such as `Cind [Hungry Bandit]`) and destination; aliases and stale identities are rejected. The driver independently reads world status, town catalog, exact actor `where`, and `stobe_state` before any chat. Native `where` must include `dist=<number>` and report no more than the supported 80-unit chat radius both before proposal and immediately before acceptance. If the actor wanders out of range, the row stops without accepting. The actor must be alive, conscious, able to take orders, and have no existing native or player order.

The driver asks the actor to offer one trip to the exact destination. It waits for the post-send native `CHAT_THREAD: Queued N streamed chat lines and N action lines` completion marker and all N queued `NPC_SAY` records before interpreting the response. It accumulates the complete stream, then sends explicit acceptance only when an exact-speaker-name and serial line contains a narrow affirmative (`I can`, `I will`, or `I'll` followed by `lead`, `guide`, `take you`, or `walk with you`) and the exact destination, without refusal or conditional wording. Refusals are reported as `PASS-DECLINED`, with no acceptance or native order; this is a separate nonacceptance outcome and is excluded from start/movement coverage. Ambiguous or incomplete speech is `FAIL evidence`, not a refusal or product failure. Immediately before acceptance, the driver rechecks exact identity, range, and state, and records position as the movement baseline. A successful row requires exactly one native `TRAVEL_LOCATION` record containing the actor serial and exact destination or its catalog coordinates. Bounded exact-handle `where` and nested-`ai` samples must report `ai.destination` within 5m of the resolved endpoint, `moving=true`, `destination_reached=false`, and `path_failed=false`. The same actor must then show at least two consecutive intervals each closer by at least 0.5m and at least 5m net progress from the acceptance-time position; tiny drift alone does not pass. Explicit `dead` or `unconscious` flags also contradict success. The reviewed AEF handler clears AI goals before calling `movement->setDestination`; its safety probe can therefore show `current_goal=OTHER`, `has_orders=false`, and `moving=true` on a valid start. The driver records those state fields but does not require a fabricated TRAVEL/MOVE goal or player-order flag. Optional `TRAVEL_TICK` lines are saved if available, but the current-build source audit found no `TRAVEL_TICK` marker in `pending-fixes/ui-hotkeys-release/exact-scope-tests/stobe/build/src` (`rg -n TRAVEL_TICK` returned no matches), so ticks are not a required signal. Arrival and changed-plan handling are follow-on rows.

Example, after the route helper and preflight:

```bash
RIG=5090 KAH_INSTANCE=3 KENSHI_DIR=/mnt/d/KenshiInst/3 \
  KAH_DIR='D:\KenshiInst\3\mods\AutomationHarness' \
  NPC='Exact current NPC name' TRAVEL_DESTINATION='Exact supported destination' \
  PREFLIGHT_RECEIPT=/path/to/fresh-preflight.txt DESTINATION_RECEIPT=/path/to/fresh-route.txt \
  OUT=/tmp/p0-travel-start-move-001 \
  NATIVE_LOG=/mnt/d/KenshiInst/3/RE_Kenshi/mods/Stobe/stobe.log \
  bash testing/live-stobe-queue/current-build-travel-driver/driver.sh
```

All raw KAH reads, requests, native log slices, and progress snapshots are retained under `OUT`. The result is `PASS-START-MOVE` only for correlated native start plus measured movement from the acceptance-time baseline; it does not claim arrival. `PASS-DECLINED` is a separate consent result and does not count as lifecycle coverage. The durable trip/agreement ledger and backend request decision remain external read-only evidence because no supported KAH ledger reader is available in this driver. Missing native serial/endpoint/position evidence fails the row; no direct travel command, order injection, or retry is used.

Run `python testing/live-stobe-queue/current-build-travel-driver/selftest.py` for mocked-handler coverage. It exercises split streamed replies where an early neutral line precedes the offer/refusal, repeated movement with `current_goal=OTHER` and no orders, natural refusals with zero acceptance/order, ambiguous wording, wrong-speaker/name/serial records, missing or misattributed start, out-of-range wandering, proposal-only movement, stationary actor, incidental tiny wander, mismatched native destination, explicit path failure, delayed duplicate start, optional tick absence, and atomic rejection of an existing output path before the first KAH call. It does not contact a rig, game, backend, service, save, or queue.
