# P0 coarse-region proposal / no-dispatch row

`region-propose.sh` is a one-turn follow-on to the frozen `current-build-travel-driver/` start/movement row. It asks the same actor about a freshly observed current region, then verifies a structured `travel_decision=PROPOSE`, speech naming that region and disclosing waypoint uncertainty, and zero native action lines. The prompt is fixed by the script: `Would you lead me to the broad area of <REGION>? This is only a question about a possible regional plan; I am not accepting or changing our current trip.` It never accepts, starts, cancels, teleports, fabricates an endpoint, or writes trip state directly.

The expectation comes from C6/R4 in `pending-fixes/live-conversation-history/COMPLEX-VALIDATION-PLAN.md` and the source operator packets: explicit regional request may yield only a coarse proposal, waypoint uncertainty must be disclosed, and proposal is not acceptance or dispatch. The row intentionally does **not** decide whether that coarse proposal replaces or coexists with the prior accepted local leg. Current `stobe_*` handlers expose no durable trip/region-plan ledger reader. The result reports both `durable_trip_ledger=UNSUPPORTED` and `active_leg_transition=UNSUPPORTED`; it proves only the live request/response/no-native-dispatch branch.

Before invoking, the rig owner must prepare fresh JSON receipts (`PREFLIGHT_RECEIPT`, `START_DRIVER_RECEIPT`, `REGION_RECEIPT`) with Unix-seconds `captured_utc` and exact shared fields: `rig`, `instance:"3"`, `npc_name`, numeric `npc_serial`/`npc_index`, `player_speaker`, `save_id`, `session_generation`, and `build_sha256`. The preflight also requires `phase:"world"`, `paused:false`, `input_isolation:"ON"`, and exact `native_log`/`backend_log` paths. The region receipt requires a nonempty `region_name` and `region_source`; `OBSERVED_REGION` must exactly match. All live receipts are limited to 600 seconds old by default.

The prerequisite is evidence from the **frozen start-driver PASS**, not a caller-asserted trip status. Its receipt must name row `P0-TRAVEL-START-MOVE-001`, result `PASS-START-MOVE`, and the frozen driver SHA-256 `EB0BA4C4F3B3F7091D1A8ED79E7CCD356823B23850B6B6885172C6B366213C70`, and point to the driver's output directory and captured result file. It also pins hashes for `accept.native.delta.log`, `endpoint.json`, `progress.json`, and the result file. The row opens those files, verifies one PASS result and one actor-serial-matched `ACTION_EXEC: TRAVEL_LOCATION` at the driver's exact endpoint. It then independently reads `status`, `stobe_ping`, exact-handle `where`, and nested-`ai` `stobe_state`; the same NPC must still be alive and moving toward the same native destination with `destination_reached=false` and `path_failed=false`. This binds the prior native start and currently active destination. It does not infer a durable accepted-trip ledger state.

Live-model execution requires a separate **opened and validated** model-readiness receipt. The preflight pins `model_readiness_receipt_path` and `model_readiness_receipt_sha256`; the row verifies the file hash, freshness, `review_status:"CLEAR"`, `model_status:"READY"`, and exact rig/instance/actor/speaker/save/session/build bindings before any KAH handler call. Missing, stale, changed, or mismatched model evidence stops as `FAIL setup`.

After one ordinary `stobe_say`, the row derives the request ID only from the fresh native `TEST_INBOX: say` record whose exact speaker, target display name, and complete message match this row. It waits for `CHAT_THREAD: Queued N streamed chat lines and N action lines` and exactly N `NPC_SAY` records, all from the exact actor serial. The backend delta must expose a structured record containing that same KAH request ID, row ID, NPC, player speaker, exact player message, and `travel_decision`. A scoped `PROPOSE` continues to product assertions; a scoped different decision is `FAIL product`; missing or unbound correlation is `FAIL evidence`, with no claim of success. The full native and backend deltas are retained. Any queued native action or `ACTION_EXEC` in the row delta is `FAIL product`.

The optional provider-fixture route is unavailable on the selected build unless exact current served-manifest membership is proven. The locally found `mechanical-provider-reply` candidate is outside the selected composition and its existing bundle has no fixture matching this region row. To use a fixture, supply a fresh `FIXTURE_SCOPE_RECEIPT` reviewed CLEAR for exact row/NPC/speaker/message/region, exact fixture ID/hash, current loaded build, served manifest and provider source hashes, and `provider_fixture_source_in_manifest:true`. The native delta must then contain a one-shot fired record matching row, fixture ID/hash, exact actor/speaker, and this request ID. Any mismatch or missing fire fails closed; it never falls back to a live provider or retries.

Only isolated i3 routes are allowed: 4080 (`KENSHI_DIR=/c/KenshiInst/3`, `KAH_DIR=C:\KenshiInst\3\mods\AutomationHarness`) or 5090 (`KENSHI_DIR=/mnt/d/KenshiInst/3`, `KAH_DIR=D:\KenshiInst\3\mods\AutomationHarness`).
