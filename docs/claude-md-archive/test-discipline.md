# Test discipline: batching, RESULT lines, efficiency, clean-up

Read before: running or judging a batch, writing a test wrapper, cleaning up after a run.
Moved verbatim from CLAUDE.md (original line numbers in the comment before each block). Nothing here is paraphrased.

- **Batch the game runs (Shay, 2026-10-03):** run as many tests as possible in one game launch, collect the bugs, fix and build them together, then restart once to install and retest. Never restart for a single fix. Start a batch as a detached WSL job, then keep a background event wait running (Shay 2026-10-14; replaces the 2-minute check-in, which woke you for every HEALTH OK; never sit on a batch that went wrong): `bash tools/automation/event-wait.sh --batch <out>` (run inside WSL, /mnt paths) ends only on an event: a batch STALL or DONE, a rig problem, an inbox message, an agent status DONE/FAILED, or the 10-minute backstop, which also runs `event-sweep.sh`. It prints one `EVENT` line; a `HEALTH OK` inside it never wakes you; `HEALTH STALL` (Kenshi gone, game on the menu/stuck, no output for 20 min) = act now (kill the stuck step or the batch, log the bug, recover the game, rerun what's left); `HEALTH DONE` = read `SUMMARY.txt`.

- **Token use (Shay, 2026-10-03):** keep context reads small (grep/tail, line ranges, never whole large files or logs).
- **Token-light tests (Shay, 2026-10-03):** save tokens by making the tests report compactly. (1) Every wrapper/scenario ends with ONE summary line per row: `RESULT <row> PASS|FAIL <key evidence: status-file value, event, inventory delta>`, plus a log path for failures (`verdict()` in `stobe-fight-lib.sh` prints it). (2) Run each batch with `tools/automation/run-batch.sh` from a short list file (one test per line; usage in its header), started detached; when `<out>/DONE` exists read only `<out>/SUMMARY.txt`. Don't hand-write batch scripts. (3) For a FAIL open only its `excerpt=` file (made by `batch-excerpts.sh`: the test's verdict lines + the error/goal/deal lines every log wrote during that test); open full logs (grep/tail) only if the excerpt doesn't explain it. (4) Hand the fixer a ticket, not a story: row, RESULT line, excerpt path, suspected component, what you already ruled out (template in `testing/AGENT_PROMPTS.md`). (5) After any server fix, the offline tests (`stobe-tests` + the regression checks) must pass before the next game batch. (6) Pack as many rows as possible into each launch (group by save); batch fixes, one rebuild/restart per batch.
- **Test efficiency (Shay, 2026-10-04):** cut invalid setup, inconclusive runs and reruns; never weaken an assertion to get a PASS. (1) Mechanical rows (guards, thresholds, pay-later, cats terms, renamed-NPC payment, prices) use the existing injection switches (`NEG_TEST_INJECT` etc.): inject the model reply *before* the logic under test so normal processing/dispatch/verification runs, confirm the injection fired, verify game/server state, restore switches on exit. A small live-model batch covers what injection can't (does the prompt produce the intended reply). (2) Shared helpers check setup before long tests (out dir, fixture, selected chars, live NPC names/handles, inventory space/items, worker awake at the bench with materials/research/power/job, game time advancing, raid protection); bounded readiness polls, not fixed sleeps; a failed setup stops that scenario with a specific reason, gets repaired, then reruns (no unchanged retries). (3) PG points keep build/config/fixture/skill/gear/setup/evidence; never reuse a stale capture after a failed command; reuse points only while code/conditions/method stay compatible; rerun single points only if independently resettable, else the block; check real state before calling a full-bench top-up a failure; 0 script failures ≠ valid balance data (investigate flat/odd values). (4) After each batch: read RESULT + FAIL excerpts, delete proven passes from the plans (evidence in the run log), classify product bug / setup failure / inconclusive / fix awaiting confirmation / unrun / Shay decision; map bugs to confirmation tests, group by fixture/build, rerun passes only when a change invalidates them; report requirement IDs and executable scenarios separately (no double counting). Don't interrupt a healthy batch for docs; never edit or replace a script a running batch is executing (on /mnt/c even .new + mv kills it, m64).

- **Clean up often (Shay, 2026-10-10: things kept being left behind for manual cleanup):** clean up after EVERY batch, review and refilm, not only at session end: superseded videos/sheets/review frames (`coordchk`), old run/take dirs, raw frames, scratch scripts, outdated docs/plan text and results nobody will read again; every agent does the same for its own outputs before reporting. Keep only what a running job writes, what's awaiting review, the final cited evidence and `C:\KenshiTestRuns\corpus\` (never cleaned). **Enforced (Shay 2026-10-10, "or it will never go away"):** `tools/automation/testruns-sweep.ps1` lists every top-level item in `C:\KenshiTestRuns`, the 4080's `C:\KAH` + `C:\KenshiTestRuns` and WSL `/root/animlab-work` (+ leaked `/tmp/animlab-*` lab temp dirs) that is off the keep-list, not named by a RUNNING agent's status/handoff, an inflight marker or a queue file, and older than 6 h (`STALE <age> <MB> <where>:<path>`); `session-start.ps1` prints it and the Stop hook blocks while any item is older than 24 h. Delete it (after `corpus.sh add` for anything a lab check cites) or record why it stays: `testruns-sweep.ps1 -Keep <path> "<reason>"` (7 days; `keep` lists, `keep clear <path>`).
- **Clean up test data (Shay, 2026-10-08; 30 GB had piled up in `C:\KenshiTestRuns`):** as soon as a row/batch is judged and its evidence is in the run log, delete what it no longer needs: run/out dirs (`m*`, `fp-*`, `vm-sweep*`, `dec-*`, crash/hang copies), raw frames/PNGs and intermediate contact sheets (keep only the few final sheets the summary to Shay cites), harness screenshots (`mods\AutomationHarness\shots`), test DLL copies, scratch scripts, the same on the 4080 (`C:\KAH`). `logs\` (launch archives, ~100 MB each) keeps only the newest 6. Never delete what a running batch writes, `game.lock`, `inflight\`, `kenshi.cfg.play`, `rig5090.idle`, `scenarios\`, `corpus\` (the animlab evidence corpus, `components/KenshiFP/animlab/corpus.sh`: before deleting a run dir, `corpus.sh add` any recording/video a lab check or Misses row uses), or fixtures. Do it at the end of every task/session, before the summary.
