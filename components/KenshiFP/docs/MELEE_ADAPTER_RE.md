## How the AI starts a swing (all paths, verified)
1. `update` (0x60CC10): picks/validates target (+0x290 Character*), runs `assessIncomingAttacks`, `_isAttacking` (+0x140) update, dead-time handling, then: state 4 -> `decisionState`; then `CombatClass::update` dispatch: state 0 -> attackState (vt+0x58), 1 -> blockState (vt+0x60), 2 -> becomes 1, 3 -> startupState (vt+0x50), 8 stumble, 6 wait, 5 circle.
2. `decisionState`: returns early if the anim is paused (0x5B2A20); sets nextMove=5, deadTimer(+0x148)=0.5, state=3, then calls `isInMeiDistance`. That checks the target is in range (dist - radius <= stats+0x150 + MEI_MAX +0x27C, not closer than +0x280), focus/target-trace rules, a stats check, movement+0x168 == 0, then calls the **target's** `whoAttacksYouOrMe(me, myAttackChance, &me->stateTimer)` and writes the result to **me->nextMove** (0 = CHOP, 1 = block, 5 = circle). If threats exist it picks nextMove=1 (block); otherwise it falls back to 5/6.
3. `whoAttacksYouOrMe` (runs on the target): gets the attacker an **attack slot** on the target (`attackSlots.addToSlotH`, +0x8), compares chances (0x6648E0), and either returns 0 (attacker swings) or makes the *target* counter: target nextMove=0, state=3 (0x6662DF). So the controlled char can also start a swing from inside an enemy's decision.
4. State 3 `startupState`: target trace blocked -> state 10; else `getStateClass(nextMove)->initialise()`; if true, state = nextMove. For nextMove 0 this is **AttackState::initialise** -> **initialiseAttack(target=+0x290)**: picks a technique by distance (stats 0x887160), sets currentTechnique +0x150, plays the anim, attackStartPos +0x15C, target +0x290, returns true. If no technique fits: calls `checkForNeedBlock(0.2, 0.05)` and **moves the character toward the target** (0x2AE8C0), returns false.
5. No other writer sets combatState=0 (scanned all `mov [..+0x1F0]/[..+0x1F4]` writes; `changeState` has no direct callers). **AttackState::initialise / initialiseAttack is the single choke point for every swing start.**

## Commitment / recovery (native, keep untouched)
- `attackState` (0x609B00) runs the technique sections (+0x268/+0x26C), the impact check, and setCombatState(4) at technique end, or early only if wantsToBlock(+0x120) and the section's cancel threshold has passed (native block-cancel).
- At technique end with stateTimer(+0x14C) <= 0: inDeadTime(+0x144)=1. While inDeadTime, `update` forces state 6 (WAIT), counts deadTimer(+0x148) down (not while the anim is paused), then state=4, inDeadTime=0.
- While state==0 and anim progress < technique+0x40, `update` does not retarget.

## Recommended adapter design
- **Ownership flag** per controlled CombatClass (getter sig from kfp_melee_observe: body(+0x648)->combatClass(+8)).
- **Hook AttackState::initialise (0x2B4AB0)**, MinHook by signature (or swap the AttackState vt slot 0x16B2BC0). `bool __fastcall(AttackState* st)`; `combat = *(CombatClass**)(st+8)`. If `combat` is manual-owned and no pending click: do not call the original; write `combat->nextMove(+0x1F4) = 6` (WAIT) and return false. This blocks AI swings from both the decision path and the counter path, and leaves stumble/block intact. Optional: call native `checkForNeedBlock(combat, 0.2f, 0.05f)` first to keep auto-block (see block below).
- **Click (M01)**: on the game thread (main-loop hook), if legal, set `pending=1` with a ~0.25 s expiry (M07 buffer: one request, no queue), then `nextMove=0; combatState=3` (the same writes the native decision makes). The next `update` runs startupState -> hook sees pending, clears it, calls the original -> native technique starts the same frame. Legal = combatModeActive(+0x130) && +0x290 != 0 && combatState in {3,4,5,6} && inDeadTime==0 && state != 0/1/2/8 && anim not paused. Never write while state 0/1/2/8 or inDeadTime: that alone means spam can't raise the rate (M02).
- **Out-of-range click (M06)**: the original `initialise` moves the character toward the target on failure (remote chase). Pre-check with native `isInAttackZone` (0x6079D0) or a distance check, or call `initialiseAttack` (0x2B4530) directly from the hook and on false return false without the approach call (re-create the hook's own failure path). Decide in game.
- **Target**: native +0x290 (set by setAttackTarget 0x664AF0, `void __fastcall(CombatClass*, Character*)`). For crosshair targeting call setAttackTarget(combat, aimed) before the click request; the AI's retarget in `update` can override it (also handle that in game).
- **Block (M03)**: the native block is reactive. `initialiseBlock` fails unless `getBiggestThreat(threats +0x220)` finds an incoming attack. Hold-RMB = each frame call `checkForNeedBlock(combat, 0.5f, 0.5f)` (`bool __fastcall(CombatClass*, float myAttackThr /*xmm1*/, float incomingThr /*xmm2*/)`; true -> it set state=3, nextMove=1), and keep wantsToBlock(+0x120)=1 so a committed swing cancels into a block only at the native cancel point. To make block *manual only*, also hook **initialiseBlock** (0x608800, `bool __fastcall(CombatClass*, bool isStumbling /*dl*/)`; 3 callers: startupState 0x60C740, blockState 0x6092DF/0x609474): if manual && !RMB && !isStumbling -> return false. Shay decides: keep AI auto-block in manual mode or not.

## Calling conventions (Win64; `this` in rcx, float args by position)
`update(this, float xmm1)`; `decisionState(this)->bool`; `isInMeiDistance(this)->bool`; `whoAttacksYouOrMe(targetCC rcx, Character* attacker rdx, float chance xmm2, float* out r9)->int`; `startupState(this)->bool`; `AttackState::initialise(AttackState*)->bool`; `initialiseAttack(AttackState*, Character* rdx)->bool` (null target -> nearest enemy in zone); `setCombatState(this, int edx)` (no-op while stumbling; for 4 it stops the technique anim); `changeState(this, int edx, float minTime xmm2)` (sets stateTimer+nextMove+state, **skips initialise**: do NOT use for CHOP, the technique would be null); `checkForNeedBlock(this, float xmm1, float xmm2)->bool`; `initialiseBlock(this, bool dl)->bool`; `blockState(this, bool dl)->bool`.

## Risks / needs an in-game trace
- +0x290 currentTarget: the observer reads 0 there, yet update/attack/isInMeiDistance use it as a live Character* and initialiseAttack writes it. Trace +0x290 during decision/attack states (maybe only set while engaged, or the observer reads too early).
- The WAIT (6) parking in the gate: check that it doesn't loop decision->startup every frame and that slot bookkeeping on the enemy (addToSlotH) doesn't make enemies wait for a swing that never comes.
- Whether the player's WASD movement (KenshiFP) fights the native movement calls in initialise/attackState (stop vcall +0x98, approach 0x2AE8C0, lookatTarget 0x665970).
- Click latency: the request is consumed on the next CombatClassAI::update of that character (per frame? confirm the call rate; periodicUpdate is separate).
- Counter path: the enemy's whoAttacksYouOrMe may return 1 (enemy blocks) expecting the manual char to attack; check that enemies don't stall in block/wait.
- Animation mods (M09) change technique tables (+0xB8 section count, +0xC0 sections): commitment stays native, but cancel thresholds differ.

## Movement findings (2026-10-05, static RE on this exe; `objdump` RVAs)
- **Approach setter 0x2AE8C0** `(CharMovement*, hand* target, float minR xmm2, float maxR xmm3, ...)`: setMovementMode(1) (0x65E680 writes CharMovement+0x378), setAnimationOverride(0) (0x65D7B0, +0x37C), then the combat mover setter 0x2AE2E0 on CharMovement+0x118 (target hand at +0x268/type +0x270, range +0x230/+0x234, strafe +0x22C). Hooked by the adapter (owned mover refused).
- **CharMovement vtable 0x16FBB58**: +0x98 halt 0x65F1E0 (mode 0, clears +0x268 target hand, pathfinder, animationOverride), +0x80 follow 0x65D9F0 (chase states 10/11 in CombatClassAI::update 0x60CFE9/0x60D006).
- **CombatClassAI::update re-enables combat locomotion every frame**: `if (state!=10 && state!=11) setMovementMode(+0x170, 1)` at 0x60CEF1. CharMovement::update 0x65F510 mode 1 branch (0x65F897) runs the combat mover update 0x2AF1A0 / 0x2AEFA0 on +0x118, which resolves its target from +0x268 **or a second hand at +0x248** (not cleared by halt or the setter) and steers into [minR,maxR]. So refusing the setter alone left the owned fighter walking toward a target 8 m away (5090 batch 1 M06: 1.4 m idle, 3 m per click). Fix: `fp_melee_hold_ground` in the KenshiFP CharMovement::update hook halts the owned mover before the update when mode==1 (or state 10/11), except during WASD drive (mode 2), CHOP/STUMBLE and anim-driven motion (+0x37C set).
- **AttackState::initialise 0x2B4AB0** success path = initialiseAttack 0x2B4530 then vt+0x98 stop, return 1 (exactly what the click path runs; nothing else is skipped, so impact/defence/damage/injury math stays native). State vtables: CircleStateAI 0x16B2B58, WaitingStateAI 0x16B2B88.
- **Swing pace**: a click is legal only in STARTUP/DECISION/CIRCLE/WAIT with dead=0 and nothing pending, so a click during the native CHOP or its dead time is rejected; the product measures CHOP time (`swing_time/swing_ends`, `last_swing_len`) and the gap between allowed swing starts (`min_swing_gap`) in game seconds.
- **Swing cancel-into-block (4080 batch 16, M04-SPEED)**: base CombatClass attack state 0x609B00 (vt+0x58 body; CombatClassAI wrapper 0x609EE0 first sets wantsToBlock +0x120 = incoming threats +0x228 > 0 and nextMove=1 if checkForNeedBlock) ends CHOP early via setCombatState(4) (stops the anim, no dead time) once the anim position (0x5B23E0, anim +0x54) passes the technique's cancel frame (tech+0xC0[hit idx]*0x14+0xC) while +0x120 is set. A natural end needs stateTimer<=0 and the anim finished (0x5B4170) and sets inDeadTime +0x144 before CHOP is left. For the owned fighter the follow-up block is refused while RMB is up, so manual swings were cut at the hit point (no block, no recovery). Fix: hook 0x609B00 (sig `40 53 56 48 81 EC 98 00 00 00 48 8B D9 48 8B 89 80 01 00 00`), clear +0x120 for the owned fighter while RMB is up (`cancel_refused` in `fp_melee state`); swingstat counts CHOP exits without dead time as `nat_cancel`, not as technique time.
- **Other native swing cuts (4080 batch 17)**: no dead time on exit from CHOP also comes from CombatClassAI::update: target KO (0x1AA0A) or target Character+0x2F8==2, once the anim passes technique+0x40 -> DECISION (0x60CCB6..0x60CD6E); target lost/stateTimer -> DECISION (0x60CF40..0x60CF72). checkForNeedBlock 0x607940 (`(cc, myThr xmm1, inThr xmm2)`: char vt+0x248 null && +0x140 < myThr && getBiggestThreat(+0x220, inThr) -> state 3, nextMove 1) is called by the AI attack state with 0.5 every CHOP frame and aborts early swings. Combat enter/exit reset 0x664F20 (r8d 0 / 2) sets state 4 + inDeadTime + clears technique (exit also sets +0x158) in one call. Natural end = inDeadTime set while state is still 0; swingstat counts only those spans. Owned + RMB up: checkForNeedBlock is refused too (`abort_refused`).
